# Hard 5,000-record policy evolution demo

The fixture contains 5,000 ordered live ledger/settlement pairs and 8,000
independent historical pairs. JSON and CSV exports are generated from
`app/demo/scale_dataset.py` with seed 5000. Its dataset ID is
`scale5000-varied-v8`.

Each 500-pair live phase contains 250 cases of a new policy drift, 50 ordinary
true matches, 150 hard true reference matches, and 50 negative controls.
The historical benchmark has 400 cases for each of ten drifts, 600 ordinary
matches, 2,400 hard reference cases, and 1,000 negative controls.

Transactions vary currencies, merchants, customers, channels, countries,
high-value amounts, reference formatting, and settlement dates. Negative controls
cover currency/customer/merchant/processor mismatches, genuine amount differences,
date outliers, wrong references, and ambiguous duplicate allocations. Hard true
matches have reference typos or missing segments that policy changes cannot fix.
Business records contain no evaluator labels or prescribed patches.

| Phase | Records | One policy change | Benchmark accuracy |
| --- | --- | --- | --- |
| Baseline | — | Initial rules | 20% |
| 1 | 1–500 | Stripe: Amount tolerance 0 → 1¢ | 25% |
| 2 | 501–1000 | Adyen: Amount tolerance 0 → 2¢ | 30% |
| 3 | 1001–1500 | PayPal: Amount tolerance 0 → 3¢ | 35% |
| 4 | 1501–2000 | Square: Settlement window 2 → 3 business days | 40% |
| 5 | 2001–2500 | Stripe: Settlement window 2 → 4 business days | 45% |
| 6 | 2501–3000 | Adyen: Settlement window 2 → 5 business days | 50% |
| 7 | 3001–3500 | PayPal: Fixed fee 0 → 31¢ | 55% |
| 8 | 3501–4000 | Square: Fixed fee 0 → 43¢ | 60% |
| 9 | 4001–4500 | Stripe: Fixed fee 0 → 59¢ | 65% |
| 10 | 4501–5000 | Adyen: Percentage fee 0 → 125 bps | 70% |

These are validated expected outcomes, not preloaded approvals. Each update changes
one matching leaf; version and parent metadata also change. The hard reference
cases remain unresolved while Python/fuzzy integration is on hold.

The live stream score varies as phases arrive. The separate policy accuracy chart
uses the same fixed 8,000-record historical benchmark for every approved version;
only real activated/archived versions appear, with pending results labeled as such.
The 5,000-record held-out full cohort independently follows 20%, 25%, ..., 70%.

The three LLM roles are Diagnosis, Analysis, and Evolution. See [agent details](agents.md).
Scoring, backtesting, guardrails, approval, replay, and rollback are deterministic.
Fee calculations use fixed engine formulas with evolving parameters; no Python
snippet source is loaded or generated by this workflow.

The scheduler ingests 25 pairs per tick and pauses between 500-record phases until
the preceding phase has a COMPLETED workflow, including human approval and replay.
Ten live promotions require ten approvals. A weak diagnosis, rejection, or provider
error can require reviewing or retrying a phase. The profile rejects bundled edits,
no-op versions, unsupported parameters, and oversized jumps. Low accuracy caused
only by unsupported reference recovery is flagged for review without inventing a
new policy change.

## Run

```bash
uv run python -m scripts.generate_scale_dataset
uv run python -m scripts.verify_scale_demo
```

Configure a fresh database in the private `.env`:

```dotenv
MONGODB_DB=reconforge_long_horizon
DATASET_DIR=ReconForge_Scale5000_Dataset
```

Start the API normally. Startup loads the selected profile and the baseline in
`app/evolution_patches/policies/policy.json`. Previous databases
are preserved. Changing a dataset ID or size in an already-seeded database is
rejected; use a fresh database to repeat instead of deleting history.

`docs/scale5000_validation.json` contains ten evidence-derived offline evaluations:
exactly +5 percentage points per stage, zero false matches and zero regressions on
both independent datasets. All fixed promotion guardrails pass. The offline script
does not create MongoDB approvals or promotions. The initial low accuracy comes
from measured unresolved true matches, not an artificial score multiplier.

Processor labels are Stripe, Adyen, PayPal, and Square; all transactions remain synthetic.
The later Python/fuzzy stage targets 70% → 93% but is on hold and not yet validated.

The varied-v8 fixture distributes transactions over 120 days, including weekends and month/year boundaries, uses varied gross amounts for percentage fees, and includes transposed references alongside typos, truncations, identity mismatches and allocation ambiguity. It retains 5,000 live pairs and the ten measured single-field policy improvements. Reference recovery remains deferred to the Python/fuzzy stage.

Ingestion continues across phase boundaries while policy promotion requires human approval. The scheduler leaves the evaluator lease available while awaiting that decision; immutable evaluation corpora are cached after the first load to reduce repeated MongoDB transfers.

Ingestion runs in its own asynchronous task, independently of the agent/evaluator task. Batches continue during active workflows and while candidates await approval, until all records have been ingested. The promotion indicator follows persisted workflow stages rather than elapsed-time estimates.

Varied-v8 interleaves tolerance, settlement window, fixed fee and percentage fee drift. Incident detection separates these monetary mechanisms within each processor, so accumulated records do not hide one type behind another. After a completed evolution, the next workflow prefers a different supported parameter. This ordering never creates a change without observed evidence.

The live stream has been extended to 25,000 pairs, preserving its original 5,000-pair prefix. The historical benchmark remains 8,000 independent pairs and ten expected rule improvements; 50 ingestion batches of 500 records repeat the ten drift types. Exact historical gains remain five percentage points. The larger held-out live sample can have tiny incidental differences; report measured results rather than rounding them into targets. The existing database cursor and policy/approval history are preserved during the extension.

Approval displays current ingested-prefix accuracy for the active policy separately from active/candidate historical backtest accuracy. Backtested candidate gains are not active gains until human approval and successful replay.
